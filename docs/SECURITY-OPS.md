# 安全告警降噪系统：从告警到规则的完整链路

## 系统要解决什么问题？

你每天在 SIEM/SOC 里看到一堆告警，其中可能 80% 都是已知的业务正常行为。这些告警：
- 不危险，但量太大把真正有威胁的淹没了
- 每次都手动关掉，但下次还来
- 新人可能不知道这是正常业务，浪费时间调查

这个系统的目标是：**自动识别"这组告警其实是正常业务"，然后建议你降噪，但不替你关。**

---

## 整体思路：别一个个看，先分组

假设你有 10 万条告警。如果一条一条分析，这辈子都分析不完。但如果能发现"这 5000 条其实都是同一个业务接口在查询"，那就只需要分析一次。

**分组逻辑就是找相似**——把 HTTP 方法、URL 模式、来源 IP 段、服务名、响应码相似的告警聚到一起。

---

## 第一步：把告警"翻译"成结构化数据

原始告警长什么样？各种格式的日志：

```
# 可能来自 Nginx
GET /api/user/profile?id=12345 HTTP/1.1 200

# 可能来自 WAF
POST /api/order/checkout 403

# 可能来自 API 网关
GET /api/health/check 200
```

系统先不管告警来源，统一提取成相同的字段：HTTP 方法、URL 路径、响应码、来源 IP、User-Agent、请求参数、服务名。这一步就是把不同格式的"方言"翻译成"普通话"，后面分析才方便。

**URL 还要做归一化处理**：把 `/api/user/12345`、`/api/user/67890` 都变成 `/api/user/{id}`，因为路径参数不同不代表是不同的请求。

---

## 第二步：按"请求签名"分组

分组不是随便分的。系统考虑几个维度：

- **请求方法 + URL 模式**：`GET /api/user/{id}` 和 `POST /api/user/{id}` 是不同的业务操作，一个查一个改，必须分开
- **服务名**：同一个 URL 在不同服务上可能是完全不同的功能
- **响应码**：200 和 500 也必须分开。为什么？因为 `/api/payment/notify` 返回 200 是"支付成功通知"，返回 500 是"支付系统挂了"——**成功率完全不同的两组告警，混在一起算出来的指标是骗人的**

举个例子：

```
组 A: GET /api/order/query → 200  → 5000 条，成功率 99%
组 B: GET /api/order/query → 503  → 13 条，成功率 0%
```

如果把 A 和 B 合并，成功率 99.7%，看起来"基本都正常"。但实际上组 B 的 13 条全是服务不可用，可能是攻击导致的，绝对不能降噪。

**这就是为什么响应码要分开**——防止高成功率的正常流量把真正异常的信号盖住。

---

## 第三步：第一轮筛选——有风险的直接排除

分组之后，系统先不做复杂分析，而是快速筛掉"明显不能降噪"的组。

三个指标，任一触发就标记整组为有风险：

| 指标 | 为什么是风险 | 举例 |
|---|---|---|
| 有确认攻击 | 安全产品已判定为真实攻击 | WAF 标记了 SQL 注入、XSS，哪怕 URL 看起来像正常业务 |
| 有恶意 IP | 威胁情报标注的 IP | 一个已知 C2 地址在访问你的正常 API——可能是探测或信息收集 |
| 有提取失败 | 连请求特征都解析不出来 | 编码绕过、畸形请求、碎片化攻击——看不懂就不能说安全 |

**这三个指标的优先级很高**，因为如果放过了：
- 确认攻击被降噪 = 漏报，你背锅
- 恶意 IP 被降噪 = 攻击者的侦察活动你看不到
- 提取失败的被降噪 = 绕过攻击成功了你还不知道

---

## 第四步：第二轮筛选——量不够的也不值得建规则

系统要求一个"值得建降噪规则"的告警组必须满足：

| 条件 | 阈值 | 安全运营角度的理由 |
|---|---|---|
| 告警数量 | ≥ 50 条 | 太少说明不频繁，不值得花精力建规则。临时出现的量小告警可能是真实事件 |
| 出现天数 | ≥ 2 天 | 只出现一天可能是攻击活动，不是稳定业务行为。持续出现的才是"已知正常" |
| 来源 IP 数 | ≥ 2 个 | 只来自一个 IP 可能是单台机器在跑脚本或者被控了。正常业务应该是多用户访问 |
| 成功率 | ≥ 70% | 成功率太低说明这个接口本身有问题。降噪等于把故障也藏了 |

**这些阈值怎么来的？** 是从实际运营经验中总结的。比如"出现天数 ≥ 2 天"——如果某个告警模式昨天第一次出现，今天就分析降噪，万一是新型攻击刚冒头，降噪等于给攻击者发了免死金牌。等它稳定出现几天，确认是业务行为再说。

---

## 第五步：Agent 分析——让 LLM 理解业务语义

通过了前面两轮筛选的候选组，才送到 Agent。这时候数据已经比较干净了，Agent 看到的是：
- 这组告警的统计数据（多少条、成功率、典型 IP 范围）
- 几条样本告警（不是全部，只给几条代表性的）
- 可用的字段列表（21 个字段，安全分析师看得懂的）

**Agent 要回��三个问题：**

### 1. 这是什么业务操作？

不是让 Agent 猜，而是让它根据 URL 模式、服务名、请求参数来推断。

比如看到：
```
URL: /api/orders/payment-status?order_id=xxx
服务: order-service
方法: GET
成功率: 98%
User-Agent: PaymentGateway/2.0
```

Agent 应该推断出："这是支付网关在轮询订单支付状态，是正常的后端回调，不是攻击者扫描。"

### 2. 什么样的告警一定属于这个业务？（must 条件）

这是 Agent 要写的"识别条件"——只有全部满足才算匹配。

比如：`service_key = order-service AND http_method = GET AND url_pattern contains /api/orders/`

注意 Agent 只能从 21 个预定义字段里选，操作符也只有 7 种：等于、不等于、在列表里、不在列表里、包含、不包含、开头匹配。**不让 Agent 写正则或自定义函数**——正则写错了可能误匹配，而且你审计的时候看不懂。

### 3. 什么情况下绝对不能降噪？（veto 条件）

即使 must 条件全满足了，如果触发 veto 条件，也必须保留告警。

比如：`is_confirmed_attack = true`——同一 URL 同一方法，但如果这条具体告警被 WAF 标记了确认攻击，就不能降噪。

**must 和 veto 的关系**：must 是"入组条件"，veto 是"例外条件"。入组了但触发了例外，还是不放。

---

## 第六步：回放验证——用历史数据"考"一下

这是整个链路里最关键的步骤，也是安全运营工程师最能理解的一步。

Agent 分析完给出的 must/veto 条件，不能直接上线。要先"回放"——拿一批独立的历史告警（Agent 没见过这批数据）来测试。

### 判定逻辑（每条告警依次判断）：

```
第 1 层：6 条红线
  命中任一条？ → 直接保留告警（KEEP_ALERT），不准降噪
  全部没命中？ → 进入第 2 层

第 2 层：must 条件
  全部满足？ → 进入第 3 层
  有没满足的？ → 保留告警（KEEP_ALERT）

第 3 层：veto 条件
  有命中的？ → 保留告警（KEEP_ALERT）
  全不命中？ → 建议降噪（SUGGEST_SUPPRESS）
```

**红线是第一道门，Agent 条件在红线之后**。意味着 Agent 分析得再好，碰到红线也得让路。

### 六条红线是什么？为什么是这六条？

| 红线 | 安全含义 | 运营视角 |
|---|---|---|
| 确认攻击 | WAF/IDS 已经判定为真实攻击 | 降噪 = 把真攻击藏了，这是事故 |
| 风险等级 HIGH | 告警置信度很高 | 即使是误报也得让人看一眼，万一不是呢 |
| 恶意 IP | 威胁情报标注 | 正常 URL 访问也可能是侦察或踩点 |
| 路径穿越 | URL 里有 `../../../etc/passwd` | 这不是任何正常业务会有的行为 |
| 危险扩展名 | 请求 `.php` `.jsp` `.asp` 文件 | 正常业务一般访问 API 路径，不会直接请求脚本文件 |
| 提取失败 | 连告警特征都解析不出来 | 看不懂的东西不能假设安全 |

**这六条红线为什么能压住安全风险？** 因为它们覆盖了攻击的几种主要信号源：产品判定（确认攻击）、置信度（风险等级）、情报（恶意 IP）、攻击手法特征（路径穿越、危险扩展名）、解析异常（提取失败）。从不同维度兜底，Agent 想漏都漏不掉。

---

## 第七步：人工审批——人做最终决策

回放通过后，系统生成分析报告：
- 这组告警是什么业务
- 统计数据（数量、成功率、时间分布）
- Agent 写的 must/veto 条件
- 回放结果（precision 是多少，有没有误降噪的）

**注意几个硬性约束：**
- **Agent 不能自己发布规则**——`PublishPattern` 这个 API 根本没开放给 Agent
- 回放 precision < 1.0 → 按钮灰掉，不允许发布
- 回放发现有确认攻击被误降噪 → 也不允许发布
- 同一组告警已经发布过规则了 → 不能再发一遍

人在 WebUI 上看报告，决定批不批。这个设计就是：**机器提建议，人做决定。**

---

## 第八步：上线后——SUGGEST，不是 SUPPRESS

规则发布后，新的告警进来，走同样的判定流程（红线 → must → veto）。

但匹配上了输出的是 `SUGGEST_SUPPRESS`（建议降噪），**不是直接消掉告警**。

这最后一步的"SUGGEST"就是整条链路的保险丝：
- 告警还在，只是打上了"建议降噪"的标签
- 你可以在 SIEM 里过滤掉这些，但原始数据没丢
- 万一出问题，回查的时候告警记录是完整的
- 审计的时候能证明：不是系统替你关了告警，是你同意了系统的建议

---

## 总结：这条链路的安全设计哲学

整个系统的设计围绕一个核心原则：**宁可多留 100 条正常告警，也不能误降 1 条真实攻击。**

体现在：
- 分组时就分开成功和失败（防止数据污染）
- 两道筛选门槛（有风险的不要、量不够的不要）
- 六条红线在 Agent 之前就兜底（攻击信号优先）
- 回放验证用独立数据"考试"（防止 Agent 过度拟合）
- 人做最终审批（机器不替人做安全决策）
- 上线后只是 SUGGEST（保留原始告警，可追溯可审计）

每一个环节都留了退路，这就是安全系统和其他系统的本质区别——**安全系统的目标是别出事，不是效率最大化。**
